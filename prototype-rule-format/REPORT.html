Issue #372 · prototype/rule-format

Burlesco Rule Format

We need one source for every site rule that builds both the userscript and the Firefox extension, with room for Chromium MV3 and uBlock Origin later. Five ways to write that rule file, compared on the same six real sites.

Recommendation: variant E, plain data grouped by target

Each site is a plain object. Anything that applies to every target sits at the top level, and anything specific to one target goes in a userscript: {…} or firefox: {…} section. Page code is written as a real function. On all six sites, E produces exactly the same techniques as D, with the same lint results. It needs no helper API, and it stays close to the shape the issue proposed.

Conditions:

  1. The build lints its own output with no-undef. That step catches the one real hazard of the function format: page code that refers to a variable from its module.
  2. The build rejects keys it doesn't know. A typo like pageIdel must fail the build, not be ignored silently. Unlike D, plain data has no function call to fail at. The prototype doesn't do this check yet.
  3. Target sections only add to the top level, never replace it. If both define pageIdle, both run, the top-level one first.
  4. When Chromium becomes a target, add a group section (extension: {…} covering Firefox and Chromium) so shared extension rules aren't copied twice.
  5. The build rejects functions it can't serialize, such as method shorthand, with a clear error. The prototype already does this.

Runner-up: variant D. It holds the same information as E, and a check on the six sites confirmed the two are identical, so converting one to the other later is mechanical. D is better only if rules start needing an explicit order for several code blocks at the same moment, or reusable bundles of techniques.

The four candidates

a-strings

Slots, code as strings

An object with fixed slots (blockRequests, pageStart, pageIdle…), with page code in template strings. This is how both repos work today.

Rejected
b-functions

Slots, code as functions

The same object, but page code is a real function that the build serializes with toString(). It's the YAML shape from the issue, written in JS.

Replaced by E
c-folders

Folder per site

site.js holds the data, and the code lives in plain script files named <slot>[.<target>].js. Shared code comes in through use: ['abril'].

Rejected
d-techniques

List of techniques

An ordered list built from helpers. Code is one kind of technique next to declarative ones like removeElements. Targets are chosen with only().

Runner-up
e-by-target

Slots grouped by target

B turned inside out: slots shared by every target at the top level, plus userscript: {…} and firefox: {…} sections that add to them. Plain data, with no helpers. (This shape was your suggestion.)

Recommended

How it was tested

I wrote the same six sites in all four formats. Each one is there for a reason: Folha uses a different technique on each target, Veja and Exame share Abril's code, JOTA injects a header in the extension and refetches the page in the userscript, Diário Popular handles cookies, and GaúchaZH is a 40-line block of code.

To compare the formats fairly, the prototype converts every variant into one common shape (an intermediate representation, or IR). That way the same emitters turn each variant into the userscript, the Firefox MV2 extension, a uBlock Origin filter list and a compatibility table. ESLint, with identical settings for all four, then runs on both the source and the generated output. Every generated file passes node --check. Nothing has been run in a browser. This compares how the formats are written and built, not whether the techniques still work.

The IR is scaffolding for this comparison only. With D, a rule file already evaluates to plain data that the emitters read, so the real build doesn't need a separate layer.

The same site in each format

Folha is the hardest case. Network blocking is the same everywhere, the userscript fakes wall.json early, and the extension reveals the text once the page has loaded. Page code is trimmed.

What the prototype found

A bug ships today in both repos, and string code hides it

GaúchaZH's code builds a style element, then calls appendChild(script). script doesn't exist, so the call throws and the CSS that hides the overlay is never applied. Both content.js and burlesco.user.js have this. Lint flags it as soon as the code is a function or a file (B, C, D: 'script' is not defined). In A it went unnoticed, the same way it has in production.

The closure trap in B and D is real, and output lint catches it

I made JOTA's userscript code refer to the module constant GOOGLEBOT instead of repeating the string. Source lint passed, because the variable exists in the module. The page never sees it, though, and linting the generated userscript reported it straight away:

output  dist/b-functions/userscript/burlesco.user.js:67  no-undef  'GOOGLEBOT' is not defined.

So the build has to lint what it emits, not just what people write. It's one ESLint call, and the prototype already makes it.

Sharing by folder pulls in too much

In C, Exame declared use: ['abril'] to get the unlock code and also got Abril's paywall-script block. Exame left Abril and has its own scripts. The check that compares each variant's IR caught this, since only C differed. Imports in B and D let a site take one piece without the rest.

Only declarative techniques reach uBlock Origin

Every variant turns blockRequests into uBO network filters. D and E also produced a cosmetic filter, because JOTA's "remove the banner" is written as data (removeElements: ['.jota-paywall']) instead of code. That comes from having the slot, not from the format: the first version of this report credited it to D alone, which was wrong. Arbitrary code can never become a filter. Every simple hide or remove technique written as data makes another future target cheap to add.

E and D hold the same information

For all six sites, E's rules produce exactly the same set of techniques as D's: the same kinds, run times, worlds and targets. The difference between them is purely how you write it: helper calls and only() in D, plain keys and target sections in E.

Generating the host check from matches removes a kind of bug

Today each site has two host lists: the manifest's matches and a separate regex in the content script. They have drifted apart. Exame's script is registered on *.exame.com, but its regex is /exame\.com\.br/, so the injection never runs. The build generates the host check from each site's matches, so there's only one list. This holds whichever format you pick.

The compatibility table comes free

Issue question 1 asks for an automatic list of which sites work on which platform. Each rule already says which technique runs on which target, so the build generates the table: dist/<variant>/COMPATIBILITY.md. It also marks request blocking in the userscript as ignored by Tampermonkey 5.2+ on Chrome (MV3). That doesn't depend on the format either.

Why not the others

D · techniques

The runner-up. It has the same information, lint and output as E, and it's the most flexible: ordered lists, groups of targets and bundles of techniques need no new syntax. The price is a helper API that every contributor has to learn, and rule files that read like code instead of data. Switch to D only if E's fixed slots start to feel limiting. Converting one to the other is mechanical.

B · functions

E is B reorganized by target. Keying each slot by target (pageIdle: { firefox }) scatters one target's work across the file. Grouping by target first (firefox: { pageIdle }) fixes that and costs nothing.

C · folders

C is the only format with nothing to serialize, and its files map directly onto MV3's files: […]. That advantage is small, though: the build can write files from B or D just as easily. The costs are bigger: twice as many files, targets hidden in filenames, all-or-nothing sharing, and an unreadable generated userscript.

A · strings

Familiar, but it keeps the problem the issue set out to fix: code that no tool can check. This prototype found a bug in production that A had been hiding.

Risks of choosing E

  • Typos in keys are silently ignored unless the build checks every key against a known list. That check is required.
  • The closure trap. Lint on the output is required, not optional.
  • How top-level slots and target sections combine has to be written down: sections add, they never replace.
  • Chromium will need an extension group, or shared extension rules get copied for each browser.
